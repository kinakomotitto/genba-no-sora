# 現場の空 — 自動検証・独自学習エンジン設計 v0.1

作成: 2026-11-09  
状態: **設計確定候補（未実装・未稼働）**  
現行アプリ: v0.8（デザイン・既存機能は変更しない）

## 目的

「現場の空」の予報を将来改善するため、**予報が発表された時点の値**を継続記録し、その後の**実際の観測値**と突き合わせて地域・季節・予報時間ごとの精度を測定する。初期段階は「一番当たりやすいモデルが何かを客観的に知る」ことを先行し、十分なデータが揃った後に限り予報の補正やモデルの重み付けを試す。

※「各社の数字の単純平均」だけでは強風・雷・大雨のリスクを消してしまう可能性があり、危険要素は範囲・最大値・公式警報を独立表示する。

## システム構成

```text
  GitHub Actions（定期実行、起動していないiPhoneと独立）
      ├─ 予報収集：MSM / ECMWF IFS / ICON
      ├─ 発表時点の予報をタイムスタンプ付きで保存
      ├─ 後日、観測データを取得・品質確認
      ├─ 予報と観測を対象時刻・単位・地点で突合
      ├─ 風・雨・気温をモデルごとに評価
      └─ 安全な集計結果だけ公開 → PWA「現場の空」に表示

  iPhone PWA
      ├─ GPS・現場名・座標・メモは端末側に保存
      ├─ 現場ごとの現在予報を表示（現行v0.8）
      └─ 学習結果の表示（将来機能：未実装）
```

### 実行タイミング案
- 最初の実験：**6時間ごと**に予報を収集（毎時00分を避け、UTCの17分等で設定）。予報モデルの実際の公開遅延に注意して発表時刻と取得時刻を区別する。
- **1日1回**の検証処理で、観測確定済みデータと突合。観測データの公開遅延や後日訂正に備えて、過去データの再検証を可能にする。
- **1週間に1回**、期間別の集計表を更新。新しい評価結果がなくても「学習済み」と偽らない。
- GitHub Actionsは無料公開リポジトリの標準ランナーで利用可能。ただし実行時刻の遅延・欠落があり得る。公開リポジトリの定期実行は60日間無活動で停止する場合もある。**警報や雨接近通知の唯一の配信基盤にしない**。
- 毎回の処理で最終成功時刻、失敗した対象モデル、最新観測時刻を記録。期限切れ・欠損・稼働停止をアプリに表示する。

## 入力データと厳格な区分

### A. 予報（過去にその時点で公表されていた値）
- モデル名・提供元・モデルの更新／初期化日時・取得日時・対象日時・緯度経度・予報リードタイム。
- 風速10m、風向10m、気温2m、時間降水量。突風予測は対応モデルのみ。**存在しない変数を0として扱わない**。
- 履歴取り込みには Open-Meteo Previous Runs / Single Runs API が技術候補。ただしライセンスとアクセス料金を確認し、**「後から現在の予報を調べた値」を当時の予報として捏造しない**。
- 同一配信基盤から取得した複数モデルは、独立したモデルでも通信の障害点は共通。

### B. 実測（検証用）
- **気象庁アメダス等の観測所**の観測値を優先。観測所ID・地点座標・標高・風速計高さ・観測時間・品質フラグ・訂正履歴も保持。
- 気象庁「過去の気象データ・ダウンロード」にはCSVと品質情報があるが、**自動化ツールによる過度なアクセスを控えるよう明記**されている。公式・適法な連続取得経路が確認できるまでは、少量の手動CSV取り込みか許諾された配信で開始する。
- ERA5などの**再解析値は推定データ**で、観測所で測定された実測値の代用品として混同しない。
- 伐採現場で観測された風はアメダス地点と異なる可能性が大きい。観測所での精度を「現場そのものの精度」と表示しない。

### C. 現場データ
- 会社の実工事名、作業員の位置、集合地点、GPS履歴、メモ、秘密情報を**公開GitHubの実行ログ・リポジトリ・集計JSONに絶対に出力しない**。
- 初期検証対象は**公開観測所・匿名の代表格子地点**。端末の保存現場はブラウザ内だけで管理する。
- 将来、現場で「雨が降った」「突風を感じた」等の任意入力を加える場合でも、**主観報告は計器観測と別区分**で評価。自動アップロードはオプトイン方式にする。

## 照合・評価ロジック

- **同じ地点（原則は観測所座標）と予報対象時刻**で比較。時刻は内部UTC保存、表示は日本時間。時間降水量は積算区間の終わりを揃える。
- 風速：MAE（平均絶対誤差, m/s）、過大／過小予測の偏り、強風時の見逃し数。閾値は社内安全基準の確認後に指定。
- 風向：0°/360°を跨ぐ**円周上の差**で評価。無風に近い際は風向精度を原則評価対象外。
- 降水量：MAE、降雨の有無の的中・空振り・見逃し。降水確率がある場合のみ、同じ時間幅・閾値に対して適切な確率スコア（Brier等）を使う。
- 気温：MAE、平均偏差。雪・積雪や山の標高による差は別途検証。
- 予報のリードタイム（例：+3h/+6h/+12h/+24h）と季節・地域で分ける。欠測は欠測として残し、勝手に補間して「正解」にしない。
- 頻発する似た天気の連続時間を独立した「サンプル数」と見なさない。検証期間の天候多様性とサンプル独立性も確認する。

## 予報の改善方法（保守的な順番）

1. **蓄積・監視だけ**（初期）：少なくとも数週間〜数か月の検証データを取り、得意不得意を可視化する。この間は予報の自動補正をしない。
2. **単純な偏り補正**：十分なデータがある地域・季節・リードタイムに限り、恒常的な過大／過小傾向の補正を実験。
3. **重み付き統合**：過去期間だけで学習して、未使用の新しい期間で評価（時系列ホールドアウト）。単純平均と単独モデルの両方を上回った場合だけ採用。評価データを学習に混ぜない。
4. **安全面の独立表示**：総合予報が改善しても、一部モデルの強い突風予測、気象庁警報・注意報、雷情報は削除・平均化しない。
5. **元に戻せる仕組み**：劣化・偏り・欠測が出たら学習済み補正を無効にし、元のモデル予報へ戻す。

## 保存と費用の設計

- GitHub Pagesは静的サイト表示用。定期処理は**別のGitHub Actions**で実施するため、アプリを閉じても処理できる。
- 無料・公開GitHubで開始するなら、**公開観測所ベースの集計結果だけ**を少量のJSONとして保存する試験から。リポジトリは非公開データベースではない。
- 長期の全時刻・全モデルの予報記録が増えたら専用DBを検討する。GitHub Actionsのartifactやcacheは永続データベースの代わりにしない。
- **商用・業務利用**のOpen-Meteo無料APIはライセンス上保証されない。実運用に入る前に利用許可とAPI代替を確保する。Windy.comのスクレイピング・無料テストAPIの数値を実測／予報の根拠に使わない。
- まず月額0円の個人検証を優先するが、安定的な通知や業務運用のために費用が必要なら勝手に課金せず相談する。

## 開発順序（推奨）

- **Phase 1 / 設計**：仕様書とスキーマ整備、データ取得ライセンス確認（いまここ）
- **Phase 2 / バッチ試作**：公開観測所3〜5地点で定期的な予報保存、取得失敗の記録。GitHub Actionsは有効化後に動作確認。
- **Phase 3 / 検証**：実測CSV取り込み＋モデル別誤差計算＋定期レポート。観測の自動取得が許可されたら自動化。
- **Phase 4 / アプリ連携**：「過去30日の検証結果」「検証地点」「評価対象の期間」を表示。まだモデル補正はしない。
- **Phase 5 / 学習**：検証で単純平均や各モデルを上回ったときだけ補正を採用。強風の安全情報は独立表示。
- **Phase 6 / 通知**：雨接近・警報通知は別の高信頼性設計で評価。定期バッチを唯一の安全監視にしない。
