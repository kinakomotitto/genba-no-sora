# 現場の空 v0.36 — 全国分散学習・試験補正・安全装置

更新：2026-11-10
状態：**個人研究用の試験補正エンジンを実装。本番の天気予報は未補正のまま。自動補正の本番開始なし。**

## 1. データ蓄積と安定化
- `tools/weather_collection_health.py` で全国観測値、3モデルの予報取得、採点結果の**更新時間**と欠測・モデル取得成功数を自動点検
- 観測/予報/採点の最終更新が概ね9時間を超える、モデルが3つそろわない、全国の有効観測数が少ない場合は `pipeline-health.json` を `degraded` にする
- 病的な異常を正常扱いしない。自動補正候補を採用できる状態にはしない
- 照合済み予報・実測ペアは**最大730日**残す。毎回巨大な月次ファイルを書き直さず、**2日遅れて日別の gzip ファイルとして確定・一度だけ保存**する
- 確定データに必要な3モデル共通の地点・時刻が最低5組なければ、日次ファイルを空や不完全な成功として確定しない
- 直近の観測データは別の短期キャッシュを維持。2日後の遅れた観測が反映されることを優先
- GitHubの公開研究データには公開観測所の情報のみ。個人GPS・保存現場名・会社現場は入れない
- 予定されたワークフローの継続成功はGitHub Actionsの実行履歴で確認し続ける必要がある

## 2. 全国のモデル検証地点を段階拡張
- 代表の**9地点**（札幌、青森、仙台、東京、名古屋、大阪、広島、福岡、那覇）を維持
- 全国アメダスの公開観測地点から、**風と降水の正常な観測値がある地点だけを追加**。地理的な距離が最大になる地点を順に選ぶ決定論的なfarthest-point法で、**最大36地点**まで自動的に広げる
- この36地点は「日本全国の地理的に分散した試験地点」を意味し、**全都道府県47の網羅ではない**。一部離島・山地の観測は十分とは限らない。全1,300地点のモデル予報を自動取得したとは主張しない
- APIに流すのは**公開アメダス観測所の座標だけ**。毎回1モデルにつき一括リクエスト1回、最大3モデル×4実行/日＝HTTP 12リクエスト相当。ただし実際のOpen-Meteoの使用量は座標の数に応じて増える（36×3×4＝**最大432地点・モデル相当/日**）
- プログラム内に**600地点・モデル相当/日のハード上限**を設置。実際のAPI側のリトライ、呼び出し計算、利用条件を考慮し、さらに拡大する前に見直す
- Open-Meteo Freeは**非商用のみ**。会社での正式運用は未許諾。勝手に有料API契約しない

## 3. 自動補正の候補を裏側だけで試す（シャドー評価）
- `tools/shadow_correction.py` を追加。**未補正の本番予報を一切変更しない**
- 同じ公開観測所・同時刻・予報対象時間の3モデルが完全にそろう履歴に限定
- **先の210日以上を学習、最後の90日を未使用検証**に分離。検証期間の観測値で補正量を決める未来情報の混入を禁止
- 雨と風の候補は**別々**に設計：
  - 風：過去の系統的偏りを中央値で求め、±1.5m/sの範囲内で補正候補を計算
  - 降水：過去に降ったデータを見ながら、0.75〜1.25倍の範囲で雨量補正候補を計算。雨の予測が0mmなら勝手に作らない（見逃しは別で評価）
- 全域、季節、月、地域、地域×季節、地域×月の区分を、十分な学習日数がある場合のみ使い、データが不足したら広域にフォールバック
- 未使用期間で、元の3モデル・中央値との精度を比較。**日単位の対応ブートストラップ**で改善の下限が正か確認
- 風速8m/s以上、1時間雨量5mm以上、降水0.1mm以上を**研究用の現象カテゴリ**として、元の予報より見逃しが増えないか確認
- 改善確認条件を満たしても、その候補を本番に配ることはない。山林・樹上の風速に一致する保証はない
- **現在のデータは2年に満たない**ため、実データから精度向上したと断言できない

## 4. 劣化したら元予報へ戻す「安全装置」の試作
- `tools/correction_guard.py` が、新しい `pipeline-health.json`、`shadow-correction.json`、既存の長期充足状況を確認
- データの更新遅延、モデル欠測、独立検証の失敗、候補の風・雨の保護条件不足を見つけたら**試験補正候補を不採用**とし `fallback_to_original_models` を出力
- 前回試験候補を承認候補としていた場合に劣化したら、`shadow_rollback_activated` を true にして理由を残す
- **本番アプリはそもそも未補正**。これは本番の補正を切り戻す実装とは違い、今の段階では**研究モードの安全装置**。本番適用用の制御は、季節を超えた独立検証、データ鮮度管理、異常時復帰を追加してから別途リリースする

## 重要な不足点・将来の精度基準
- 季節をまたぐ十分な観測期間が必要。現時点では季節別の補正効果を証明できない
- 直近90日の検証だけでは春夏秋冬すべてに対する補正性能を保証できない。**過去の複数時点に分割したローリング検証**を追加し、各季節・地域での悪化を評価する必要がある
- 全国の代表36地点だけで、全国すべての場所・山・森林の気象の確度が保証されるものではない
- 強風・豪雨・降雪などの希少事象は、通常の平均誤差より厳しい見逃し評価と十分なイベント件数が必要
- モデル構成・バージョン変更の検知、観測所の測器条件、積雪・降雪の別評価も次段階
- **自動補正の完成通知**はChatGPT側で週次確認登録済み。今回のv0.36は完成条件ではないので通知しない

## v0.36.1：予報APIが不安定なときの段階的復旧

最初の全国36地点一括取得で3モデルとも正常応答が得られなかった。通信元や外部APIの失敗原因は未確定だが、再び1つの大きな失敗で全地点の予報が消えないように対策した。

- 取得対象は**最大9観測所の小さなバッチ**に分割し、地点ごとにモデルの成功/失敗を記録する
- 1日4実行、最大16GET/回、最大36地点。バッチの中で正常に取得できたモデルの予報は保存する
- 直前に3モデルとも成功していれば**9→18→27→36**と一段ずつ拡張
- 3モデルの一部に不調があれば段階を戻し、全失敗なら次回は**9地点まで戻して再試行**
- 途中取得に失敗しても、欠測を0とはみなさない。少なくとも3モデルが同じ条件でそろう地点しか「公平な精度検証」として数えない
- APIの正常応答が得られなければ、学習の自動進行は止まる。実際の公開データの連続成功が確認されるまでは「全国36地点の予報収集が安定稼働」とは宣言しない
- もともとの全国アメダス**実測データの低頻度収集**と、この予報APIの拡張処理は独立している

この修正はOpen-Meteoの仕様に沿った**非商用の小規模試験**の範囲にとどめるもので、APIへの大量アクセスや料金契約を許可するものではない。

## v0.36.2：本番収集の起動時刻を厳格化

- 本番の全国気象収集は**UTC 00:12、06:12、12:12、18:12（日本時間 09:12、15:12、21:12、03:12）のGitHub Actions予定実行**と明示的な手動実行だけ。コードをGitHubに送っただけでは**外部APIへアクセスしない**
- GitHubのプログラム変更時は、無料の外部気象APIを使わない**オフライン自動テストだけ**実行
- 6/12/24時間先の照合時刻に合わない予定外の実行では、未来の天気を取得して誤った期間として採点するのを禁止。データを取得せず「時刻不一致」と記録
- GitHub Actions自体の実行遅延が1時間を超えた場合も誤った予報時刻として記録しない。取得を見送ったときは次の予定実行で再挑戦
- 以前はPRやデータ更新のたびに何度も外部予報APIへアクセスしていたため、通信失敗やAPI制限の原因になった可能性がある。ただしHTTPError/URLErrorの詳細原因は確定していない
