# 現場の空：標高 × 昼夜 × 観測気温の自動研究（第1段階）

## 目的
山間地・谷地形における気温変化の傾向を、**現場へ行かず**全国の気象庁アメダス観測から調べる。箱根湯本の「アプリ気温と小田原の実測」「標高差約87m」という利用者の気づきが発端だが、その2地点の差だけで気温逆転・予報誤差を確定しない。

## 何を自動実行するか
既存の「全国アメダス・３モデル予報の自動検証」GitHub Actions（予定: JST 03:12 / 09:12 / 15:12 / 21:12）に**追加の研究手順**を組み込む。

1. 従来どおり気象庁ホームページの公開データを取得。既存の1回最大3 HTTP GETを変更せず、`amedastable.json`から観測所の地表標高 `alt` を`latest.json`へ保存する。端末GPS・作業現場・個人の検索履歴は取得しない。
2. 最新の気温測定が有効で標高も分かる観測所から、**25km以内で標高差70〜800mの組を最大160組**、重複しないよう決定する。標高や温度が欠けた場所は使わない。
3. 過去14日以内に保存済みの品質チェック済み実測気温から、**同じ観測時刻の2つの観測所の気温差**（高い観測所−低い観測所）を集計。異なる日の測定値や未来の予報と混ぜない。
4. 日本時間06:00〜17:59を便宜上「昼」、18:00〜05:59を「夜」として傾向を分ける。夜は両地点の10分平均風速がともに2m/s以下か、それ以外かも分ける。**日出・日没の時刻に基づく分類ではない**。
5. `data/model-validation/terrain-temperature-research.json` に件数・日数・高い観測所が暖かかった割合・気温差の平均と中央値を記録。個人位置情報や観測所の生データを再アップロードすることはない。
6. 十分な日数・独立した測定時刻がない場合は`collecting_observations`、一定の蓄積ができても`exploratory_diagnostics_only`と表示する。

**研究結果はユーザー向け予報の値を変更しない。自動補正はOFF。** 長期の季節別検証・気象モデルの温度誤差分析は後続段階で、今回の追加には含まない。

## データ上の重要な限界
- 高い観測所のほうが暖かい観測があっても、それだけで**逆転層や冷気だまりの発生を証明したことにはならない**。別々の観測地点には地形、斜面方位、土地被覆、建物、風・日照の差がある。
- 異なる地点の気温差は**ある地点の予報誤差ではない**。予報の自動補正に使うには、同地点・同時刻・予報取得時刻をそろえた独立データと季節別検証が必要。
- 空が晴れているか、実際の谷地形、雲量、風による混合は現データでは判定できない。雨量0mm≠晴天。研究に記載の「夜」は便宜上の固定時刻。
- 全観測所の中から比較可能な組を選択し、気温欠測地点は除くため、**全国を均等に代表する統計ではない**。
- 元の全国観測履歴は約14日でローテーションするので、今回は直近2週間の**移動窓の研究**。年単位・季節単位の結論や標高補正の根拠としない。
- GitHubの定期実行には遅れや未実行があり、収集データが不十分なら不足として扱う。自動研究が失敗しても既存の全国収集やプッシュ通知を止めない。
- 観測出典：気象庁ホームページのアメダス公開データを加工。学術研究や安全判断に使う際はデータの原本・時刻・計器品質を再検証すること。

## エラーと監視
2026-11-13 03:58 JSTのモデル収集はMSMが一部HTTP 400（18地点のうちMSM成功9）。ECMWF/ICONは18地点成功。既存処理にはモデル失敗時に対象地点数を減らす自動バックオフがあるため、今回の研究導入ではモデル収集APIを変更しない。3回連続障害を満たさない限り専用インシデントを新規作成しない既存条件を守る。

## 品質管理
- `tests/test_amedas_snapshot.py`：観測所標高の数値と異常値の検証。
- `tests/test_terrain_temperature_research.py`：時間の一致、昼夜、弱風、欠測、不正値、標高ペア、個人GPSを含まないこと、研究用のフラグ固定、14日の履歴と出力。
- 定期ワークフローとプルリクエストの両方でオフラインテストを実行。観測所・時刻の実データによる集計は**次回の実際の収集が成功してから**反映される。
